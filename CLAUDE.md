# Downtify Android — conventions

Native Android client for the Downtify self-hosted music server. Kotlin, Jetpack Compose + Material 3, Hilt, Media3, Room, DataStore. See README.md for build and setup.

## The server contract

- The contract lives in the server repo: `~/git/downtify/docs/mobile-client-contract.md`, with details in `docs/api-reference.md` ("Server and sign-in", "Mobile API (v1)", "WebSocket") and user-facing behaviour in `docs/features/mobile-apps.md`.
- **Don't invent endpoints.** The app only calls what the server really has. If the app needs something the server doesn't offer, add it to the server in the same task (see [Server and client together](#server-and-client-together)); `docs/server-requirements.md` is for what is left for later.
- When the docs and the server code disagree, the code wins; fix the server's docs to match it.
- To test against the server, run it with `DOWNLOAD_DIR`/`DATABASE_DIR` pointed at a scratch directory and a spare `--port`; port 8000 may be the user's own instance. From 3.2 a fresh server has accounts: sign in as `admin`/`downtify` (`POST /api/auth/login`, keep the cookie, send an `Origin` header) to create pairing codes with `POST /api/auth/pairing`.
- Every request carries `Authorization: Bearer <token>` (`AuthInterceptor`), even when the server doesn't require sign-in: a 401 is how the app learns it was unpaired. A 401 "revoked", a WebSocket close 4401, or a refused WebSocket handshake confirmed by `GET /api/auth/status` all end the session (`SessionStore.onRevoked`).

## Modules and dependency rules

```
:app ──► :core:designsystem
     ──► :core:player ──► :core:data ──► :core:network ──► :core:model
```

- `:core:model` is pure Kotlin (JVM): no Android imports. Put logic here whenever it can live without Android — it's the cheapest place to test. It runs on Android too, so no JVM APIs newer than API 26 (e.g. `URLEncoder.encode(String, Charset)` is API 33 — use the `"UTF-8"` overload). Android lint does not check this module; be careful.
- `:core:network` knows the wire format (DTOs, Retrofit interfaces, WebSocket, NSD). DTOs never leave it: map to `:core:model` types. Two interfaces: `DowntifyApi` for the mobile client contract (`/api/v1`, sign-in and pairing, listens, activity) and `WebApi` for the web app's own routes a device may call (search, downloads, queue, podcasts, Discover). `ApiFactory.createWebPatient` is for calls the server answers only when it's done (an episode download, Discover's first run). `TrashApi` (`ApiFactory.createTrash`) holds the music trash part of the contract, apart from `DowntifyApi` only to keep each interface under detekt's size limit.
- `:core:data` owns persistence and the sync/report logic. Repositories expose `Flow`/`StateFlow`; the UI never touches DAOs or the API directly.
- `:core:player` owns Media3. The UI talks to playback only through `PlayerController`.
- Screens live in `:app` under `feature/<name>/` (Screen + ViewModel). There are no feature modules yet: at this size they'd add build config without buying isolation. Split a feature out when it gains its own data layer (e.g. offline downloads).
- Gradle config goes in the convention plugins in `build-logic/`; versions only in `gradle/libs.versions.toml`. Check current stable versions before bumping — don't guess.

## Architecture

- Single activity, Navigation Compose with type-safe `@Serializable` routes (`ui/navigation/Routes.kt`).
- MVVM + unidirectional data flow: a ViewModel exposes one `StateFlow<XUiState>`; the screen calls ViewModel functions for events.
- Split every screen into a `XRoute` (gets the ViewModel, collects state) and a stateless `XScreen(state, callbacks…, modifier)` that previews and tests can call directly.
- **Text fields:** keep the text in synchronous snapshot state (`var x by mutableStateOf("")` in the ViewModel, or a plain `MutableStateFlow`), never in a flow that went through `combine`/`stateIn` — the async hop drops keystrokes. Don't rewrite the typed text (e.g. uppercase) in `onValueChange`; use a `VisualTransformation`.
- Coroutines: `viewModelScope` in ViewModels, the `@ApplicationScope` scope for app-lifetime work. Rethrow `CancellationException` from every broad `catch`.
- Android 17+ (target 37): talking to anything on the LAN needs the runtime `ACCESS_LOCAL_NETWORK` permission. The connect screen asks for it before starting NSD discovery.
- Server search and requests: `CatalogRepository` and `ServerQueueRepository` (`:core:data/catalog`). The web API's song objects aren't versioned like `/api/v1`: read them leniently (`CatalogJson`) and send them back to the server untouched (`RemoteSong.raw`), never rebuilt from the app's fields. The queue is read-only for devices.
- Podcasts (`PodcastsRepository`) and Discover (`DiscoverRepository`) go through `callServer`/`ServerResult` like the catalog. A device can only read podcasts, download an episode and save progress — subscribing is admin-only, so don't offer it. An episode is a media item with id `episode:{id}` (`EpisodeIds`) playing the server's file; anything that assumes a media id is a library track (likes, lyrics, listens, the notification's heart) must check `EpisodeIds.isEpisode` first. Progress is saved by `EpisodeProgressTracker` in the service, not the UI.
- Now Playing and the mini player are one surface: `PlayerExpansion` says how far it's open (0–1, saved across recreation) and `ExpandingPlayer` draws the morph (bounds and corners from the mini player's card to the window, the two players' content fading, the cover flying between them). Open and close Now Playing only through `PlayerExpansion` (`expand`/`collapse`), so a tap, the collapse button, a drag and predictive back all move the same surface; the mini player marks its place with `Modifier.miniPlayerAnchor`.
- Previews play in `PreviewPlayer`, never through the media session: they must not reach the queue, the notification, listens or activity reports. Clips come from third-party CDNs — only `AuthInterceptor` adds the token, and only for the paired server; keep it that way.
- Offline copies: `OfflineRepository` (in `:core:data/offline`) owns them. What should be on the phone is a pure `OfflinePlan` (`:core:model`) computed from the kept collections, the library, the files and the limit; the repository deletes what the plan drops at once and hands downloads to `OfflineSyncWorker`. Don't write offline files from anywhere else. The offline tables are user data: change them with Room migrations (`autoMigrations`), never by bumping the version and relying on the destructive fallback.

## Theming and UI

- Use the real Material 3 components; no look-alikes. Colors come from `MaterialTheme.colorScheme` — never hard-code hex values in screens. Brand tokens live in `core/designsystem/theme/Color.kt` (dark is the default look; light matches `Tokens.dc.html`). Dynamic color is opt-in (Settings).
- The theme is `MaterialExpressiveTheme` with `MotionScheme.expressive()`: animate through `MaterialTheme.motionScheme` (spatial springs for size, position and corners; effects springs for color and opacity), not hand-picked tweens.
- Type: by default Google Sans Flex, always its rounded cut (ROND axis at 100), as a Google downloadable font — `theme/Type.kt` — on the v3 scale (36 sp bold `displayMedium` page titles, semibold headlines, 18 sp `titleMedium`, 16/14 sp labels, and the emphasized styles one weight up). The user can switch to Downtify classic (Sora for display/headline/titleLarge, DM Sans for the rest; saved as `Downtify`) or the system font (`AppFont` in `:core:model`, `downtifyTypography(font)`). `DowntifyType` has what the M3 scale lacks: the wide hero title (Google Sans Flex at wdth 151, rounded too, whatever the font setting) and the `data*` styles that every technical value uses (durations, bitrates, sample rates, sizes, formats): the app's own face with tabular figures (`withDataValues` for values inside a sentence). No monospaced face anywhere: the owner wants one font throughout. Don't set a `fontFamily` in a screen unless it is a preview of a choice.
- Pure black (`amoled` setting): `ColorScheme.amoled()` in `theme/Theme.kt` turns the dark background and base surfaces black and darkens the raised ones; `MainActivity` also paints the window black. Use `surfaceContainer*` roles for cards so they stay visible on it.
- Settings and About use `GroupedList` (`ui/common/GroupedList.kt`), a thin wrapper over Material 3 Expressive's `SegmentedListItem` (there is no `GroupedListItem` in Material 3). It needs **material3 1.5.0-beta01** (`libs.versions.toml`); BOM-resolved 1.4.0 doesn't have it. Move to the stable 1.5 when it ships. Shapes in `theme/Shape.kt`: the M3 Expressive corner scale, `DowntifyShape` for the named ones (section 24, hero 32, list cover squircle 22 %, big cover 28, floating bar and mini player `BarCorner` 28, meeting at `JoinedCorner` 10 where the mini player sits on the floating bar) and `ListStyle` for grouped lists (segmented 24/8 gap 4 for settings, separated 24 gap 8 for content, compact 16/4 gap 2). Spacing on a 4 dp grid via `Spacing`.
- Now Playing, the mini player, the album header and the lyrics take a whole color scheme from the cover: wrap them in `CoverTheme(coverUrl)` (`component/CoverScheme.kt`), a nested theme whose scheme is Material's tonal spot seeded with the cover's Palette swatch (`material-color-utilities`), animated on the slow effects spring. Their background is the cover's `primaryContainer`, the play button its `primary`; without a cover they keep the app's scheme. Pure black doesn't apply there: the cover's color is the point.
- Icons: Material Symbols Rounded as vector drawables in `:core:designsystem` (`DowntifyIcons`), outlined at rest and filled when selected.
- The bar and rail have three tabs (Home, Search, Library). Everything else that needs a way in from the top goes in the side menu (`AppDrawer` in `ui/navigation/`, a `ModalNavigationDrawer` over the whole shell, opened only from Home's menu button): add it to `DrawerDestination`, and give its screen a back button, as Downloads has.
- Edge-to-edge: pad with `WindowInsets`, don't fight the system bars. 48 dp minimum touch targets. Every screen works in `NavigationBar` (compact) and `NavigationRail` (medium+). In compact the bar floats as a pill by default (`floatingNavBar` setting, read through `LocalFloatingNavBar`); off, it spans the screen's width. Artist, album and playlist pages hide the bar on phones: only the mini player stays. On the floating bar the mini player joins it as one group (`attached`). The content runs on behind the mini player and the floating bar, as in PixelPlayer: every scrolling screen pads its list's end with `.plusBottomBars()` (`LocalBottomBarsInset`, `ui/common/BottomBarsInset.kt`) so its last item can scroll clear of them.
- Every user-visible string goes in `app/src/main/res/values/strings.xml` **and in the eight translations** (`values-bg|el|es|fr|hu|pt-rBR|ru|tr`): the languages of the Downtify web app, English being the fallback and `resources.properties`' default. The web app's German and Korean locales exist in the server repo but aren't translated here yet — add `values-de`/`values-ko` and their `localeFilters` before offering them in the app. Lint fails on a missing translation. Keep `localeFilters` in `app/build.gradle.kts` in step with the folders (it also feeds `generateLocaleConfig`, the per-app language list). Strings that must not be translated (brand names, the license name) are `translatable="false"`. Plurals need `one` and `other`, plus the extra forms of the language (`few` and `many` for ru). Take the web app's terms (`~/git/downtify/frontend/src/i18n/locales`) when a word exists there.
- `app/src/main/res/raw/license.txt` is a copy of the repository's `LICENSE` (the License screen shows it); `LicenseTextTest` fails when they differ.
- Each screen and component has `@PhonePreviews` previews (`:core:designsystem`: light and dark at 360 and 412 dp, where values must not break), the screens' built from `ui/common/PreviewData`.
- The v3 components live in `:core:designsystem/component`: `Artwork` (cover or honest tonal placeholder, squircle by default), `PageHeader` + `CircleButton` (one row as the library's: back, a 36 sp title, actions; circular 48 dp buttons; pair it with `pinnedScrollBehavior`), `PillTabs`, `Tag`, `ChoiceGroup` (one of a few options as a connected button group: the theme, Downloads' tabs), `SectionCard` + `KpiTile` + `IconAvatar`, `HeroHeader`, `OnboardingFooter` + `ShapeIllustration` (the connect screen's steps: a 96 dp next button that changes shape per step, a picture in Material shapes that shrinks to the room it's given). The connect steps don't scroll: the picture takes what the header and form leave and goes when that's too little, the other ways in step aside while the keyboard is up, and `ConnectScreenFitTest` checks every step fits 360 × 640 dp in every language — keep their texts short, `MediaListItem` (content rows; `TrackItem`/`CoverItem` in `ui/common/LibraryItems.kt` build on it; `TrackItem` draws what's playing as PixelPlayer does, a pill in `primaryContainer` with a round cover, and has a `compact` form for the library's songs), `VerticalScrollbar` (a draggable scrollbar for a lazy list or grid, placed in the list's end padding; its geometry is `ScrollMetrics` in `:core:model`), the player's `MiniPlayerCard` (transport only: previous, play/pause, next; the title is a `MarqueeText`), `PlaybackControls`, `PlayerToggles` and `WavySeekBar`, and `EmptyState(hero = true)`. Use them instead of rebuilding one in a screen.

## Testing and quality

- `./gradlew build` must pass (compile, unit tests, Android lint). `./gradlew detekt spotlessCheck` must be clean; `spotlessApply` formats.
- Unit tests: JUnit 4 + Turbine + fakes (MockK only where a fake is awkward). Pure logic gets tests in `:core:model`; sync and the listen queue are tested in `:core:data` against in-memory fakes.
- Compose UI tests run on the JVM with Robolectric (`app/src/test`, SDK 34 — newer sandboxes need a Java 21 test JVM). Test the stateless `XScreen`s.
- When a change affects behaviour against the server, verify it for real (emulator + a scratch server instance) and say exactly what you ran and what you didn't.

## Final reply

Every task ends with a reply that lets the maintainer check the change by hand, in this order:

- **How to test it.** Concrete steps, not "run the tests": the commands (`./gradlew build detekt spotlessCheck`, a single `./gradlew :core:model:test --tests '*TrashTest'`, `./gradlew installDebug`), the server setup it needs (a scratch instance as in [The server contract](#the-server-contract), an env var such as `DOWNTIFY_TRASH=true`, an admin pairing), what to do on the phone or emulator, and what they should see when it works. Say which of these you already ran and which are left to them.
- **Where it shows in the interface.** When a screen changed, name the way in, then the screen and the control: the tab (Home, Search, Library) or side menu entry, the screen, and the menu, sheet, dialog or setting — e.g. "Library → any song's ⋮ menu → _Move to trash_" or "side menu → Trash, the _Restore_ button on each row". Say who sees it (admin pairings only, servers with a capability, a setting that must be on, phones vs. the navigation rail). When the server's web UI changed too, say where there (page and route). If nothing visible changed, say so in one line.
- Then name every repo changed and its `commit-message.md`.

## Releases

- The version lives only in `app/build.gradle.kts` (`versionName`, and `versionCode`, which must rise with every release). Publishing a GitHub release tagged `v<versionName>` builds and attaches the signed APK in CI. Steps and the one-time key setup: `docs/releasing.md`.
- The release build is minified by R8: a library that works by reflection needs a keep rule in `app/proguard-rules.pro`. Run the release APK on a device (pair, sync, play, open the QR scanner) after adding a dependency.

## Server and client together

The Android client lives in `~/git/downtify-android` (this repo), the server in `~/git/downtify`. They evolve as one product: when a task here needs a change on the other side — a new or changed `/api/v1` endpoint or field, a WebSocket frame, a server bug the app runs into, contract docs that are wrong — make that change in `~/git/downtify` in the same task, without stopping to ask. A session opened in the server repo may change this one the same way.

- Before editing the other repo, read its `CLAUDE.md` and follow it there (ruff, tests, docs and translations rules, its quality bar). A server change the app relies on gets its docs (`docs/mobile-client-contract.md`, `docs/api-reference.md`) and tests in the same change. Installed apps keep calling the old shape, so add fields and endpoints rather than renaming or removing.
- **Don't commit, stage or push, in either repo.** The maintainer commits by hand.
- **No change goes undescribed.** Every edit to tracked files (code, tests, docs, config) is described in `commit-message.md` at the root of the repo it touched (git-ignored in both). A task that touched both repos leaves a message in each, and each mentions the other side ("Needs the server's …" / "Used by the Android app's …").
- Write it before the final reply, as Conventional Commits (`feat:`, `fix:`, `build:`, `docs:`, `test:`, `refactor:`): imperative subject ≤ 72 characters, a body saying why, then what changed per file or area.
- The file may hold an older message. If `git log` already has its subject, it was committed: replace it. If it describes changes still uncommitted, keep them: extend the message to cover everything pending, or add a separate message for unrelated work, separated by a `---` line and each naming the files it covers.
- End the reply by naming every repo changed and its `commit-message.md`.
